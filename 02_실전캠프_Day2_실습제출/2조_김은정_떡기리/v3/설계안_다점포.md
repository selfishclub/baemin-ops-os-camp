## 1. 변경된 전체 구조

### 1-1. 지금(v2) → 바꾼 뒤(v3) 한눈에
| | v2 (지금) | v3 |
|---|---|---|
| 지점 구분 | 매장 이름 글자 | 지점 고유번호(store_id) + 직원 링크용 코드(6자리) |
| 데이터 접근 | 앱이 표를 직접 읽고 씀. 익명이 전부 허용 | 앱은 표를 직접 못 읽음. "지점 코드(또는 PIN·로그인)를 넣어야 답하는 서버 함수"만 호출 |
| 매뉴얼 | content.md를 코드에 구움. 수정 = 재배포 | 본사 공통(DB) + 지점 추가사항(DB). 본사 화면에서 수정 → 즉시 반영 |
| 직원 입장 | 첫 화면 → 매장 고르기 → 이름 고르기 | 지점 링크/QR → 이름 고르기(매장 안 고름) |
| 점주 | PIN 4자리, 전 매장 공용 | 지점마다 PIN 6자리, 자기 지점만 |
| 본사 | 없음 | 이메일 로그인, 전 지점 현황·매뉴얼 편집·지점 등록 |

### 1-2. 세 역할과 들어가는 길
```
직원  …/#/s/AB7K2Q        → 이름 고르기 → 매뉴얼(공통+우리 지점) · 오픈/마감 체크 · 특이사항 · 교육표
점주  …/#/s/AB7K2Q 맨 아래 "점주" → PIN 6자리 → 점검표 · 직원 · 우리 지점 추가사항 · 설정 · 직원용 링크/QR
본사  …/#/hq              → 이메일 매직링크 → 지점 목록 · 지점 상세 · 공통 매뉴얼 편집 · 지점 등록/중지
```
- 코드 없이 그냥 주소로 들어오면 "매장 QR이나 링크로 들어와 주세요"만 보임(지점 목록 노출 없음).
- 김은정 사장은 본사 관리자이자 직영 3곳 점주. 직영 3곳은 같은 PIN을 넣어 두고, 전체는 본사 화면에서 봄.

### 1-3. 섞이지 않는 원리(권한)
① 모든 표에 `store_id` 칸
② 익명(anon)의 표 직접 접근 정책을 마지막 단계에서 삭제
③ 직원용 함수는 `code`를 받아 그 지점만 답함. 점주용은 `code + PIN`(해시 대조, 5회 실패 시 10분 잠금). 본사용은 로그인 이메일이 `hq_admins`에 있을 때만
④ 앱 코드를 다 뜯어봐도 "코드 없는 지점"은 가져올 방법이 없음

## 2. 본사 공통 매뉴얼 + 지점별 추가사항 — 데이터 구조

### 2-1. 두 표로 분리
```
manual_pages            본사 공통 매뉴얼 (장 단위)
  id, chapter_no int, group text, title text, body_md text, sort int,
  updated_at, updated_by(이메일)

store_manual_notes      지점별 추가사항 (지점 × 붙일 자리)
  id, store_id FK→stores, chapter_no int, section_key text,   ← 붙일 자리: 장 + 소제목(예 "② 주방 정리"). 비우면 장 맨 끝
  body_md text, kind text('add'),                              ← 지금은 '추가'만. '대체'는 열어 두지 않음(아래 2-4)
  sort int, active bool, updated_at, updated_by(점주/본사)
```
- `group`: 요청하신 6묶음 꼬리표. 브랜드 교육(1장) / 기본 운영수칙(2·3·5장) / 제품관리(6·9장) / 고객응대(7·11장) / 위생(8장) / 포장(6장 포장 부분) / 오픈·마감 원칙(4·10·12장). 장 번호는 그대로 두고 묶음은 목차에 표시만.
- `section_key`: 매뉴얼 안의 굵은 소제목 글자(예 `② 주방 정리`). 점주는 화면에서 드롭다운으로 고르기만 함. 본사가 소제목 이름을 바꾸면 그 추가사항은 자동으로 "장 맨 끝"으로 내려가고 점주 화면에 "위치 확인 필요" 표시.

### 2-2. 지점 전용 체크 항목(기존 기능 유지)
```
store_settings          지점 설정
  store_id PK, extra_items jsonb {open:[...], close:[...]},   ← 지점 추가 체크 항목(주기 표기 "(매주 월·목)" 유지)
  products jsonb [...],                                       ← 떡 종류(폐기 입력용)
  info jsonb {hours:"", notes:""}                             ← 운영시간 등 짧은 정보(선택)
```
- "매뉴얼 추가사항"(읽는 글)과 "체크 항목"(누르는 칸)은 따로 둠. 공항점 "냉장고 확인 후 사진 1장"은 매뉴얼 추가사항으로도, 마감 체크 항목으로도 넣을 수 있음(점주가 선택).

### 2-3. 나머지 표
```
stores        id uuid PK, brand('떡기리'), name, code UNIQUE(6자리), owner_name, owner_phone,
              owner_pin_hash, pin_fail_count, locked_until, status('active'|'paused'), created_at
staff         id uuid PK, store_id FK, name, hire_on date, active bool, UNIQUE(store_id, name)
hq_admins     email text PK, name            ← 로그인 이메일로 대조
checklist_runs     (기존) + store_id FK, UNIQUE(store_id, run_date, kind). 기존 store 글자 칸은 그대로 둠
training_progress  (기존) + store_id FK, staff_id FK, UNIQUE(staff_id, step)
settings / sales   (기존) 그대로 둠. v2가 끝까지 읽을 수 있게
```

### 2-4. 왜 '대체(오버라이드)'는 안 넣는가
- 점주가 본사 기준을 가려 버리면 "본사 공통은 전 지점 동일"이 깨짐. 운영시간·할인·배달앱·쓰레기 배출처럼 요청하신 예시는 전부 "추가"로 충분.
- 정말 다르게 해야 하는 지점이 생기면 본사가 공통 문구를 "지점별 기준에 따름"으로 고치고 각 지점이 추가사항을 쓰는 방식으로 해결. `kind` 칸은 남겨 두어 나중에 필요하면 켤 수 있음.

## 3. 직원 화면에서 합쳐 보이는 예시

### 3-1. 규칙
- 매뉴얼을 열면 공통 본문을 그대로 보여 주고, 그 지점의 추가사항을 **해당 소제목 바로 아래** 연한 색 상자로 이어 붙임. 상자 제목은 "📍 우리 지점 추가사항".
- 소제목 지정이 없는 추가사항은 그 장 맨 끝에 같은 상자로.
- 다른 지점 추가사항은 애초에 받아오지 않음(서버 함수가 code 기준으로만 돌려줌).
- 검색도 공통+우리 지점 추가사항을 함께 검색. 결과에 "우리 지점" 꼬리표.

### 3-2. 공항점 직원이 10장 마감 매뉴얼을 열었을 때
```
10장. 마감 매뉴얼                                   ← 본사 공통

② 주방 정리
 □ 튀김기 주변·설탕통·스텐 집기 세척
 □ 견과류 등 냉장 보관
 □ 오늘 폐기 수량을 마감 체크리스트 "오늘 폐기" 칸에 입력
 □ 떡 날짜 표기, 싱크대 설거지·음식물 처리
 ┌ 📍 우리 지점 추가사항 ───────────────────────┐
 │ 냉장고 확인 후 지정 위치(냉장고 문 안쪽) 사진 1장을 │
 │ 남긴다. 사진은 공항점 단톡에 올린다.                │
 └──────────────────────────────────────────┘

③ 앞카운터 정리
 …

⑥ 최종 퇴실
 □ 뒷문·앞문·주방 뒷문 잠금 확인
 ┌ 📍 우리 지점 추가사항 ───────────────────────┐
 │ 공항 보안구역 출입증은 퇴실 전 반납함에 넣는다.       │
 │ 건물 출입 가능 시간 06:00~23:00                     │
 └──────────────────────────────────────────┘
```
상동본점 직원이 같은 10장을 열면 공통 본문은 똑같고, 상자 내용만 상동본점 것(예: "배달앱 접수 마감 21:30에 '영업 종료' 전환")으로 바뀜. 추가사항이 없는 지점은 상자가 안 보임.

### 3-3. 오픈·마감 체크리스트
- 공통 항목(본사) 뒤에 지점 추가 체크 항목이 지금처럼 이어 붙음. 지점 항목에는 작은 "우리 지점" 꼬리표.

## 4. 점주 관리자 화면 구조 (`#/s/코드` → "점주" → PIN)
```
점주 홈 (지점명 표시)
├ 점검표          날짜 이동 / 오늘 오픈·마감 상태 / 기록 카드: 담당자·완료시간·체크 수·미완료 항목·특이사항·폐기
├ 직원            이름 추가·수정·퇴사(비활성), 입사일, 교육 진도(1·3·7일, 7일 배지, 사수 확인)
├ 우리 지점 추가사항
│  ├ 매뉴얼 추가사항   [장 고르기] → [소제목 고르기(또는 '장 맨 끝')] → 내용 → 저장 / 목록에서 수정·끄기 / 미리보기
│  └ 체크 항목         오픈 추가 항목 · 마감 추가 항목 (주기 표기 안내) · 떡 종류
├ 설정            PIN 바꾸기(6자리), 운영시간 등 짧은 정보
└ 직원용 링크/QR   링크 복사 · QR 이미지 저장/인쇄 · 카톡 안내문 복사
```
- v2 "사장 점검표"에서 **빠지는 것**: 매장 목록 편집, 직원별 소속 선택, 매장 열(지점 하나니까 불필요)
- 공통 매뉴얼은 읽기만. "본사 공통 내용은 본사에서 관리합니다" 안내 한 줄.

## 5. 본사 관리자 화면 구조 (`#/hq`, 이메일 매직링크)
```
본사 홈
├ 지점 목록       지점명 · 점주 · 코드 · 상태 / 오늘 오픈 ○△✕ · 마감 ○△✕ / 교육 진행률(직원 n명 중 m명 완료) / 최근 특이사항 1줄
│   └ 지점 상세   그 지점의 점검표(점주와 같은 화면, 읽기) · 직원 · 추가사항 보기 · PIN 초기화 · 사용 중지/재개 · 링크/QR
├ 공통 매뉴얼     장 목록(묶음 꼬리표) → 장 본문 편집(마크다운 textarea + 미리보기) → 저장(수정 시각·수정자 기록)
│                 └ 수정 이력: 장별로 날짜·수정자 목록 → 내용 비교 → "이 버전으로 되돌리기"(되돌린 것도 이력에 남음)
│                 "저장하면 모든 지점에 바로 반영됩니다" 확인창
├ 지점 등록       지점명 · 점주 이름 · 연락처 → 코드 6자리 + 첫 PIN 자동 생성 → 점주에게 보낼 안내문 복사(링크·PIN·시작 순서)
└ 특이사항 모아보기  최근 7일 전 지점 특이사항·폐기 (선택 기능, 1차에서는 지점 목록의 1줄로 충분하면 생략)
```
- 매직링크 흐름: 이메일 입력 → 메일의 링크 클릭 → 로그인 완료. 등록된 본사 이메일(hq_admins)이 아니면 "권한 없음".
- 본사 관리자는 김은정 1명으로 시작. 추가는 SQL 한 줄(또는 본사 화면에 나중에).

### 5-1. 신규 점주 시작 과정(본사 등록·승인 방식)
① 본사가 지점 등록(= 승인) → 코드·첫 PIN 생성
② 본사가 점주에게 안내문 전송(링크 + PIN + 순서)
③ 점주가 링크 → "점주" → PIN → 직원 등록, PIN 변경
④ 점주 화면에서 직원용 링크/QR 복사·인쇄 → 직원에게 공유
⑤ 직원이 링크 열고 이름 선택 → 사용 시작

## 6. 기존 직영 3개점 데이터 이전(보존)

### 6-1. 원칙
- **옮기는 게 아니라 "새 칸을 채운다".** 기존 표·기존 칸·기존 줄은 지우지 않음. v2 앱은 옛 칸(`store` 글자, `settings`)을 계속 읽으므로 끝까지 정상 동작.
- 실행 전 Supabase에서 4개 표를 CSV로 내보내 `v3/백업/날짜/`에 보관(저장소에는 안 올림. 직원 실명 포함).
- SQL은 한 벌(`migrate_v3_step1.sql`)로 만들고 **트랜잭션 1개** 안에서 실행 → 중간에 실패하면 전부 취소됨.

### 6-2. 순서
| 순서 | 하는 일 | 확인 |
|---|---|---|

### 6-3. 이전 중·후 v2와의 호환
