## 2. 백업 검증 방식 (`inspectBackup`)

읽기만 한다. 저장소를 건드리지 않는다 (테스트 1-3).

| 순서 | 검사 | 결과 |
|---|---|---|
| 1 | JSON 파싱 | 실패 → 거절 "잘렸거나 다른 파일" |
| 2 | 앱 식별자 `app === "sootdak-ledger"` | 아니면 거절 |
| 3 | 버전: 숫자이고 지원 목록(1)에 있어야 | 없음·0·2 → 거절. 더 큰 버전은 "앱을 먼저 새로 받으세요" |
| 4 | `data` 가 객체 | 아니면 거절 |
| 5 | 항목 10개 각각: 있으면 목록이어야. **거래(transactions)는 필수** | 거래 없음 → 거절. 나머지 없음 → 기본값(규칙은 기본 규칙, 그 외 빈 목록)으로 채우고 **채운 항목을 화면에 명시** |
| 6 | 줄 단위: 식별자·날짜(`YYYY-MM-DD`)·달(`YYYY-MM`)·금액 숫자·출처 값 | 틀리면 거절 (최대 12개까지 이유 나열) |
| 7 | 중복: 거래 id · 일별매출 (날짜·채널) · 직원 id · 규칙 id · 채널매출 (달·채널) · 마감 달 · 올린 기록 id · 설정 key · 날씨 날짜 | 거절 |
| 8 | 참조: 근무가 가리키는 직원이 없음 | **경고만** (지운 직원일 수 있어 복원은 허용, 인건비 0원 안내) |
| 9 | 저장 시각 없음 | 경고 |

**호환성**: `exportBackup()` 이 만든 파일을 그대로 다시 읽을 수 있음 (테스트 1-2). 형식(`app`·`version`·`savedAt`·`data`) 불변.
**누락 처리 방침**: "조용히 빈 배열"은 없다. 필수(거래)는 거절, 나머지는 채우되 미리보기에 "파일에 없어서 기본값으로 채우는 항목" 으로 표시.

## 3. 복원 절차 (RestoreDialog)

파일을 고르면 창이 열리고, **쓰기는 마지막 "복원 실행" 한 번뿐**이다.

1. **검사** — 위 2절. 거절이면 이유 목록과 닫기. 장부 그대로.
2. **미리보기** — 저장 시각 · 버전 · 파일 크기 · 항목별 **현재 장부 vs 파일** 표(줄어드는 항목은 빨강) · 거래 있는 달 · 일별 매출 기간 · 설정 이름 · 채운 항목 · 경고 · "현재보다 오래된 백업" 경고 · **복원하면 사라질 수 있는 것**(파일에 없는 달, 줄어드는 건수, 파일에 없는 설정) · 사진 연결 경고(5절) · "사진은 이 파일에 없고 지워지지 않음" 안내. 버튼: 취소 / 내용을 확인했어요 → 다음.
3. **확인** — 현재 장부가 비어 있지 않거나 손상 상태면:
   - "현재 장부 백업 파일 받기" (손상 상태면 "손상된 원본 내려받기 .txt") 버튼. 누르면 "브라우저는 실제 저장을 알려 주지 않으니 다운로드 폴더를 열어 확인" 안내.
   - 체크박스 "다운로드 폴더에서 파일이 저장된 것을 직접 확인했어요" — 프로그램이 검증할 수 없으므로 **사람의 확인을 따로 받는다**.
   - 글자 입력칸에 **"복원"** 을 쳐야 함.
   - 둘 다 돼야 "복원 실행" 버튼이 켜진다 (`canRestore`, 테스트 7·8, 브라우저 확인).
   - 현재 장부가 비어 있으면 잃을 것이 없으므로 바로 실행 가능.
4. **실행** — `applyBackup`: `setItem` 한 번. **지우고 다시 쓰지 않는다** (테스트 9-2에서 `removeItem` 호출 없음 확인). 실패하면 "복원하지 못했어요. 현재 장부는 그대로예요" + 원인.
5. **취소** — 어느 단계든 창만 닫힌다. 저장소 불변 (테스트 7, 브라우저 확인).

## 4. 복원 실패 시 데이터 보존 검증

- 자동: 가짜 저장소의 `setItem` 이 공간 부족 예외를 던지게 한 뒤 `applyBackup` → `StorageFullError`, 원래 값 그대로 (테스트 9·10).
- 브라우저(3201): 가짜 장부 거래 3건 → 가짜 백업(거래 1건)으로 복원 시도, 쓰기 직전에 공간 부족을 흉내냄 → 창에 "복원하지 못했어요. 현재 장부는 그대로예요 (… 2KB, 584B …)", 저장소 거래 여전히 3건. 이어서 정상 복원 → 1건, "복원했어요".

## 5. 손상된 장부 복구 검증

- 손상 복구 화면(StorageGuard)의 "백업 파일로 복원" 이 같은 RestoreDialog 를 연다. 미리보기에 "읽을 수 없는 상태라 비교 불가. 덮어쓰면 손상된 원본은 사라져요" 경고, 확인 단계의 사전 백업 버튼이 **"손상된 원본 내려받기 (.txt)"** 로 바뀌고 체크 문구도 "손상된 원본 파일을 확인했어요" 로 바뀜. "복원" 입력 전까지 버튼 꺼짐, 손상 원본 문자열 그대로 (브라우저 확인).
- 자동: 손상 상태에서 검사·적용이 되고, 적용 전엔 손상 원본이 그대로 (테스트 11).

## 6. 영수증 사진 연결 위험

**구조 (코드로 확인)**: 사진은 IndexedDB `sootdak-ledger-photos` 에 `{id, ownerId, name, type, size, addedAt, blob}` 로 있고, `ownerId` 는 **영수증(매입) id** 또는 **고정비 id** 다. 둘 다 localStorage 의 설정(`purchases_YYYY-MM`, `fixed_costs`) 안에 있다. 사진을 지우는 코드는 영수증·고정비를 지울 때(`deletePhotosOf`)와 새 영수증 편집 취소 때뿐이다.

| 질문 | 답 |
|---|---|
| JSON 복원이 사진을 지우나 | **아니오.** 복원은 localStorage 한 키만 쓴다. IndexedDB 는 건드리지 않는다 |
| 거래 식별자 변경으로 연결이 끊기나 | 통장 거래(transactions) id 와 사진은 연결되지 않는다. **영수증·고정비 id** 가 바뀌거나 파일에 없으면 끊긴다 |
| 사진 없는 영수증·주인 없는 사진이 생기나 | 다른 기기의 백업을 불러오면 "영수증은 있는데 사진 없음", 지금 장부에만 있던 영수증이 파일에 없으면 "사진은 있는데 영수증 없음(고아)" 이 생긴다. 고아 사진은 지워지지 않지만 화면에서 보이지 않는다 |
| 복원 전후 위험 | 위 고아 사진. 되돌리려면 사전 백업 파일로 다시 복원하면 연결이 돌아온다 (사진이 그대로이므로) |

**구현**: 미리보기에서 이 브라우저의 사진 수를 세어(`countPhotosByOwner`) 복원 뒤 연결이 끊길 장수를 계산하고(`photoLinkRisk`, 테스트 12), 있으면 빨간 경고 "영수증 사진 N장은 복원 뒤 연결이 끊겨요 (지워지지 않지만 보이지 않아요)". 사진이 없으면 경고 없음. 항상 "사진은 이 파일에 없고 지워지지 않음" 안내.
D단계(사진 백업·복원)에서 manifest 에 `ownerId` 를 담아 이 연결을 같이 보존해야 한다.

## 10. D단계 진행 전 확인 사항

1. **사진 백업 형식**: ZIP 을 쓰려면 압축 패키지(예: `fflate` 또는 `jszip`) 설치가 필요합니다. 설치 전에 패키지 이름·이유를 보고하고 승인받겠습니다. 패키지 없이 가려면 "사진 1장 = 파일 1개 + manifest.json" 을 여러 번 내려받는 방식이 됩니다(사진 많으면 불편).
2. **manifest 에 담을 것**: 사진 id · ownerId(영수증/고정비 id) · 파일명 · 형식 · 크기 · 해시 · 백업 시각 · 앱 버전. 장부 백업과 짝을 맞출 수 있게 장부 백업의 `savedAt` 도 넣을지.
3. **사진 복원 시 기존 사진 처리**: 같은 id 는 덮어쓸지 건너뛸지(제안: 건너뛰고 개수 보고).
4. **부분 저장 위험(7절)** 을 D단계 뒤 별도 단계로 다룰지.
5. 사장님 브라우저에 사진이 몇 장, 몇 MB 있는지 — 규칙 탭에는 아직 표시가 없습니다. D단계에서 표시를 넣겠습니다. **[확인 필요: 대략 장수]**
