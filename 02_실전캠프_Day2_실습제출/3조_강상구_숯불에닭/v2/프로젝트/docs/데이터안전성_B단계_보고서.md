## 2. 손상 감지 구현 방식

**빈 장부와 손상된 장부를 세 갈래로 나눴습니다** (`inspectLocal()`):

| 저장소 상태 | 결과 | 앱 동작 |
|---|---|---|
| 키가 없거나 빈 문자열 | `ok: true, empty: true` | 정상 빈 장부 (기본 분류 규칙만) |
| JSON 이고 모양이 맞음 | `ok: true, empty: false` | 정상 |
| JSON 이 아님 / 목록이어야 할 항목이 목록이 아님 / 장부가 아닌 값 | `ok: false, kind: "damaged", raw: 원본` | 아래 "손상 처리" |
| 브라우저 저장소에 접근 불가(시크릿 창 등) | `ok: false, kind: "unavailable"` | 접근 안내, 쓰기 차단 |

**손상 처리**
- `readLocal()` 은 전처럼 빈 장부를 돌려주지 않고 `StorageDamagedError` 를 **던집니다.** 그래서 어떤 코드도 빈 장부로 착각해 덮어쓸 수 없습니다. 모든 쓰기(`LocalStore.update`)는 읽기를 먼저 거치므로 **쓰기 전부가 막힙니다.** 원본 문자열은 한 글자도 바뀌지 않습니다 (테스트로 확인).
- 읽기도 던집니다. 빈 배열을 돌려주지 않으므로 "손상인데 0원으로 보이는" 화면이 생기지 않습니다.
- `AppShell` 이 처음 열릴 때와 저장 실패가 날 때마다 `inspectLocal()` 을 부릅니다. 손상이면 **모든 화면(children)을 렌더링하지 않고** 복구 안내만 띄웁니다. 따라서 호출부 40여 곳의 읽기 실패 처리 방식과 상관없이 어떤 화면도 뜨지 않습니다. 띠는 빨간색 "입력이 잠겼어요".
- 복구 안내에 **손상된 원본 내려받기**(.txt, 원본 그대로) · **백업 파일로 복원**(기존 `importBackup`, 유일하게 열어 둔 쓰기 경로) · **다시 확인** 버튼.

## 3. 저장 실패 처리 방식

- `writeLocal()` 이 `setItem` 실패를 받아 종류를 가립니다. 공간 부족이면 **지금 사용량과 저장하려던 크기**를 담은 `StorageFullError`. 브라우저는 실패 시 이전 값을 그대로 두므로 기존 데이터는 보존됩니다 (테스트로 확인).
- `LocalStore.update()` 가 실패를 `notifyStorageFailure()` 로 알린 뒤 **그대로 다시 던집니다.** 기존 catch 동작은 유지되고, catch 가 없는 화면에서도 알림이 뜹니다.
- `AppShell` 의 빨간 알림: "저장되지 않았어요 (시각) · 원인 · **화면에 보이는 값은 아직 저장 전이에요**". 사장님이 닫기 전까지 남습니다.

**"저장된 것처럼 보이는" 경로 점검** — 저장 호출 약 40곳을 전부 읽었습니다.

| 유형 | 곳 | 처리 |
|---|---|---|
| 저장을 기다린 뒤 화면을 바꿈 (실패하면 성공 표시 안 됨) | 채널 정산 저장, 오늘 마감 저장, 올리기, 원가율 전부, 영수증, 지급일, 분류 규칙, 마감, 직원, 날씨 등 | 그대로 둠. 실패 시 알림만 추가됨 |
| **화면을 먼저 바꾸고 저장** (실패해도 저장된 것처럼 보였음) | 규칙 탭 고정비 · 오늘 탭 채널 설정 · 정산 규칙 · 공휴일 · 정산 조정 · 비율 기준 · 손익분기 설정 (7곳) | **실패하면 이전 값으로 되돌리고** 오류를 다시 던지게 고침 |
| 실패를 삼킴 | 손익분기 카드 `.catch(() => {})` | 되돌리기로 교체 |

## 4. 저장 공간 표시 (규칙 탭)

- 장부 크기 · 전체 사용량 · **"약 5MB (추정)"** · 비율 막대. 글자 수 × 2 바이트로 어림하고, "브라우저가 정확한 한도를 알려 주지 않는다"고 화면에 적음.
- 80% 넘으면 노랑, 95% 넘으면 빨강 + 정리 안내.
- 마지막 백업: **내려받기를 시작한 시각**으로 기록. "파일이 실제로 저장됐는지는 다운로드 폴더에서 확인" 문구. 기록 없음 또는 7일 이상이면 경고.
- 이 시각은 장부 덩어리 밖 별도 키(`sootdak-ledger-last-backup`)에 두어 **백업 파일 형식이 바뀌지 않음** (테스트로 확인).

## 6. 기존 기능 영향

- 계산 모듈·화면 구성 변경 없음. 기존 테스트 335개 전부 통과.
- 저장 인터페이스(`Store`) 시그니처 불변 → 시연 모드(Supabase) 코드 무변경.
- 백업 파일 형식(`app`·`version`·`savedAt`·`data`) 불변. 예전 백업 파일을 그대로 불러올 수 있음.
- 정상 상태에서 달라지는 것: 규칙 탭 카드 하나, 백업 안내 문구, 실패 시 빨간 알림. 그 외 화면은 똑같음.
- 7곳의 "먼저 바꾸고 저장" 동작은 성공 시 전과 같고, 실패 시에만 되돌림.

## 7. 미해결 위험

1. **콘솔 오류.** catch 없이 저장을 부르던 화면(채널 정산 등)은 실패 시 브라우저 콘솔에 "Uncaught (in promise)" 가 찍힙니다. 사장님 화면에는 빨간 알림이 뜨므로 사용에는 문제없지만, 깔끔하게 하려면 그 화면들에 catch 를 더해야 합니다. 이번엔 손대지 않았습니다.
2. **여러 번 저장하는 흐름의 부분 저장.** 오늘 마감(일별 매출 → 근무), 올리기(거래 → 올린 기록), 영수증(여러 설정)은 저장을 여러 번 부릅니다. 두 번째에서 실패하면 첫 번째는 이미 저장된 상태입니다. 알림은 뜨지만 "절반만 저장"을 되돌리지는 않습니다. 한 번의 쓰기로 묶으려면 저장 인터페이스를 바꿔야 해서 보류.
3. **손상 감지 시점.** 처음 열 때와 저장 실패 때만 확인합니다. 앱이 열린 채로 다른 탭이나 프로그램이 저장소를 깨뜨리면 다음 저장 시도 때 잡힙니다(그때 쓰기는 막힘).
4. **한도는 추정.** 5MB 는 흔한 값일 뿐 브라우저·버전마다 다릅니다. 실제 한도는 실패가 나야 압니다.
5. **백업 시각은 "시작" 시각.** 파일이 실제 저장됐는지는 알 수 없습니다. 화면에 그렇게 적었습니다.
6. **복원은 아직 옛 방식.** 검사·미리보기·확인창 없이 덮어씁니다. C단계에서 고칩니다. 손상 복구 화면의 복원 버튼도 같은 함수를 씁니다.
7. **사진(IndexedDB)** 은 이번 범위 밖. 백업 설명에 "사진은 안 들어간다"는 문구만 추가.

## 8. 운영 반영 전 참고
