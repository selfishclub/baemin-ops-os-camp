## 2. 원자적 저장 구현 방법

`LocalStore.update()` 는 원래부터 "읽기 → 바꾸기 → `setItem` 한 번" 이었습니다. 문제는 화면이 그것을 **여러 번** 불렀다는 것뿐입니다. 그래서:

1. 바꿀 내용을 **작업 목록(BatchOp)** 으로 표현한다. 거래 upsert · 올린 기록 추가 · 그날 매출 통째 교체 · 그날 근무 통째 교체 · 설정 upsert.
2. `applyOps(data, ops)` 가 장부 한 덩어리에 목록을 차례로 적용한 **새 덩어리**를 만든다(순수 함수, 입력 불변).
3. `LocalStore.batch(ops)` = `update(d => applyOps(d, ops))` → `setItem` **한 번**. 브라우저의 `setItem` 은 성공 또는 실패(이전 값 유지)뿐이므로 **전부 되거나 전부 안 된다**.
4. 세 화면이 낱개 호출 대신 `batch` 를 부른다. 영수증은 조건에 따라 1~3개 작업을 목록에 담아 한 번에.
5. 낱개 저장 함수도 `applyOp` 를 쓰게 바꿔 두 길의 결과가 같음을 테스트로 고정했다.

부수 효과: 자동 백업의 "장부 바뀜" 신호가 작업 수만큼이 아니라 **한 번**만 난다(테스트). 실패한 batch 는 신호를 내지 않는다.

## 3. LocalStore 와 Supabase 각각의 보장 범위

| 저장소 | `batchAtomic` | 보장 | 비고 |
|---|---|---|---|
| **LocalStore (내 PC 모드 = 운영)** | `true` | 작업 목록 전체가 `setItem` 한 번. 공간 부족·손상·기타 실패 시 **한 글자도 안 바뀜** (테스트로 원본 문자열 동일 확인) | 운영에서 쓰는 유일한 저장소 |
| **SupabaseStore (시연 모드)** | `false` | **원자적이지 않음.** 표마다 요청을 보내므로 i번째에서 실패하면 앞의 i−1개는 남는다. 오류 메시지에 "N개 중 i개는 이미 저장됨" 을 적어 상태를 숨기지 않음 | 시연 모드는 **가짜 데이터 전용**(로그인 없음)이라 운영 데이터 영향 **없음**. 진짜 원자성을 내려면 Postgres 함수(RPC)에 작업 목록을 JSON 으로 넘겨 한 트랜잭션에서 쓰도록 `supabase/schema.sql` 에 함수를 추가하고 `batch` 가 `rpc()` 를 부르게 해야 한다. 시연 DB 에 접속해 시험할 수 없어 **이번에는 구현하지 않았다**. 임시 구현을 "안전"으로 표시하지 않는다 |
