## 4. 장부·사진 복구 검증 (실제 연결)

가짜 장부(거래 89·일별 매출 102·근무 40·직원 3·설정 7) + 사진 3장(영수증 p1·p2, 고정비 f1 에 연결) 로:

1. 통합 백업 → 서버 검증 완료 (manifest `mode: full`, 사진 3).
2. **해시 3중 일치**: 브라우저가 보낸 바이트 = 폴더의 파일(`sha256sum`) = manifest 기록 (장부 `f0ad6b46…`, 사진 `2a6b7c08…`).
3. 빈 저장소 준비: localStorage 비움 + 사진 DB 삭제 → 앱이 "빈 장부"로 뜸.
4. 장부 JSON 복원(RestoreDialog): 미리보기 현재 0 → 파일 89/102/3/40/7, 빈 장부라 즉시 실행 가능 → 복원.
5. 사진 ZIP 복원(PhotoRestoreDialog): 3장 검사 통과, 새 3장, **연결됨 3장**, 넣기 → 3장.
6. **원본과 비교**: 장부 10개 항목(거래·규칙·채널매출·마감·올린기록·일별매출·근무·직원·설정·날씨) 각각 JSON 해시 **전부 일치**. 사진 3장 **바이트 해시·ownerId 전부 일치**, 모든 사진이 복원된 장부의 영수증·고정비에 연결됨.

## 6. 부분 저장 위험 분석 (B단계부터 미해결)

재현 테스트 `lib/storage/partialSave.test.ts` 4개 추가 (두 번째 저장에서 공간 부족을 일으킴):

| 흐름 | 저장 순서 | 두 번째 실패 시 상태 | 영향 |
|---|---|---|---|
| 오늘 마감 | 일별 매출 → 근무 | 매출만 저장, 근무 없음 | 인건비 누락. 빨간 알림은 뜨고 "저장됨" 표시는 안 됨. 다시 저장하면 둘 다 덮어써서 복구됨 |
| 올리기 | 거래 → 올린 기록 | 거래만 저장 | 같은 파일을 또 올리면 중복 경고가 안 뜸 → 거래 중복 가능 |
| 영수증 | 영수증 목록 → 품목 단가 → 통장 줄 분류 | 통장 줄만 예전 그대로 | 그 줄이 "확인 필요"로 남음. 돈이 두 번 세이지는 않음 |

**권장 수정안** (구조 변경이라 이번엔 적용하지 않음): `Store` 인터페이스에 `batch(fn: (data) => data)` 같은 "한 번의 쓰기" 함수를 추가하고(LocalStore 는 이미 private `update` 가 그 역할 — 테스트로 전부 되거나 전부 안 됨을 확인), 위 세 화면이 그것을 쓰도록 바꾼다. Supabase 저장소에도 같은 이름의 함수(순차 호출)가 필요하다. 예상 작업: 저장소 2파일 + 화면 3파일, 테스트 포함 반나절.

- 규칙 탭: 저장 공간 카드(사용량·마지막 백업), 영수증 사진 카드(장수·용량), 자동 백업 카드 "켜짐" + 폴더 표시.
- 8초 뒤 자동 통합 백업 → 카드 "서버 검증" 시각 표시 → 폴더에 파일 3개.
- ★ **실제 데이터로 복원 검증은 하지 않는다.** 대신 백업 폴더의 ledger JSON 을 **3201(개발)** 에서 RestoreDialog 로 열어 미리보기까지만 보고 취소(쓰기 없음) → 거래·매출 건수가 실제와 맞는지 확인. 이것도 실제 숫자를 개발 브라우저에 올리는 일이라 ★ 승인 필요.
- 손익·오늘·올리기·정산·원가율 탭을 한 번씩 열어 화면 정상.

### 롤백
| 상황 | 방법 |
|---|---|
| 화면 오류·이상 | 운영 저장소 `git checkout main@{1}` 또는 `git reset --hard <merge 이전 커밋>`(히스토리 유지 위해 `git revert -m 1` 권장) → 서버 재시작. 데이터는 브라우저에 그대로 |
| 자동 백업이 문제 | `.env.local` 의 `BACKUP_DIR` 줄 삭제 → 서버 재시작 → 카드 "꺼짐". 코드는 둬도 됨 |
| 장부가 이상하게 보임 | 1단계에서 받은 JSON 으로 규칙 탭 복원(미리보기·사전 백업·"복원" 입력) |
| 사진이 이상함 | 복원·백업 코드는 사진을 지우지 않음. 그래도 걱정되면 `IndexedDB` 는 건드리지 않고 코드만 롤백 |
