## 1. 기존 앱 기술 구조

### 한 줄 요약
손익장부는 "서버가 없는 앱"입니다. 화면 코드가 사장님 브라우저에서 돌아가고, 숫자도 그 브라우저 안에 저장됩니다. 인터넷으로 나가는 요청은 날씨를 받아오는 것 하나뿐입니다. **[확인]**

### 기술
| 항목 | 내용 |
|---|---|
| 프레임워크 | Next.js 14.2 (App Router), React 18, TypeScript 5.5, Tailwind 3.4 **[확인]** |
| 엑셀 읽기 | SheetJS (xlsx). 은행·포스 파일은 브라우저 안에서만 읽음 **[확인]** |
| 서버 코드 | 없음. `app/api` 폴더는 비어 있음. 로그인·권한 없음 **[확인]** |
| 외부 연결 | Open-Meteo 날씨 API 한 곳 (무료, 열쇠 없음). `lib/weather.ts` **[확인]** |
| 검사 도구 | `npm run typecheck`, `npm run test` (vitest, 테스트 파일 38개, 계산 모듈만 검사) **[확인]** |
| 실행 | 3200 포트 dev 서버 상시 실행 중. **빌드는 돌리면 안 됨** (과거 사고 2회) |

### 화면 구성
하단 탭 6개: 손익(/) · 오늘(/today) · 올리기(/upload) · 정산(/channels) · 원가율(/costing) · 규칙(/rules). **[확인]**
탭 없이 들어가는 화면: 날씨(/weather, 오늘 탭 카드에서 진입) · 연간(/year) · 사용법(/guide). **[확인]**

탭 목록은 `components/AppShell.tsx` 의 배열 한 곳에 있어서 한 줄만 더하면 탭이 생깁니다. 다만 폰 화면에서 탭 6개가 이미 꽉 차 있어, 7번째 탭보다는 날씨처럼 "카드에서 들어가는 화면"이 어울립니다. **[추정]**

### 데이터 모양 (`lib/types.ts`)
| 이름 | 무엇 | 단위 |
|---|---|---|
| DailySale | 일별 채널 매출 (날짜·채널·금액) | 하루 × 채널 1줄 |
| Transaction | 통장 한 줄 (분류 포함) | 거래 1줄 |
| ChannelSale | 달별 채널 주문금액·정산금액 | 달 × 채널 1줄 |
| Shift / Staff | 근무시간 · 직원(별칭·시급) | 하루 × 사람 1줄 |
| DailyWeather | 일별 날씨 (맑음·흐림·비·눈, 최고·최저, 강수량) | 하루 1줄 |
| Setting | 이름표 달린 설정값 (채널 목록, 정산 규칙, 공휴일 목록 등) | 키 1개 |

- **시간대별 매출은 없습니다.** 하루 단위가 가장 잘게 쪼갠 단위입니다. **[확인]**
- **공휴일은 사장님이 정산 탭에서 날짜를 손으로 적는 목록**입니다(`settings` 의 `holidays`). 정산일 계산에만 쓰이고, 매출 분석에는 아직 안 쓰입니다. **[확인]**

### 이미 있는 "상권분석 비슷한" 기능
| 기능 | 위치 | 하는 일 |
|---|---|---|
| 날씨 × 매출 | `lib/weather.ts`, `app/weather/page.tsx` | 과거 날씨를 자동으로 받아 날씨별·요일×날씨별 평균, 비 오는 날 효과, 30도 이상 효과 |
| 예보별 예상 매출 | 같은 곳 `expectedSales` | 7일 예보를 받아 "같은 요일·같은 날씨 평균"을 참고값으로 표시. 오늘 탭 카드에도 뜸 |
| 요일별 평균 | `lib/weekday.ts` | 영업일만 세어 요일별 평균·배달 비중. 가장 센 요일·약한 요일 |

즉 **작업 3의 3번(날씨)·4번(요일)·7번(당일 예상)의 뼈대는 이미 있습니다.** 새 모듈은 이걸 갈아엎는 게 아니라 "외부 변수를 더 붙이는" 방향이 맞습니다.

## 2. 기존 데이터 저장 및 백업 상태

### 저장 방식 두 가지 (`lib/storage/`)
| 모드 | 언제 | 데이터가 있는 곳 | 실제 숫자? |
|---|---|---|---|
| 내 PC 모드 (기본) | 사장님 PC에서 3200 포트로 열 때 | 그 브라우저의 localStorage, 키 이름 `sootdak-ledger-v1` 한 덩어리 **[확인]** | 예 |
| 시연 모드 | `.env.local` 에 `NEXT_PUBLIC_STORAGE=supabase` + 열쇠 2개 | Supabase (인터넷). 로그인 없어 누구나 봄 **[확인]** | 아니오, 가짜만 |

- 두 모드는 같은 `Store` 인터페이스를 쓰므로 화면 코드는 어느 쪽인지 모릅니다. 새 모듈도 이 인터페이스를 통해 읽으면 두 모드에서 똑같이 동작합니다. **[확인]**
- 사진만 따로 IndexedDB에 둡니다(장부 덩어리가 커지지 않게). **[확인]**
- Vercel 시연 사이트(sootdak-ledger.vercel.app)가 시연 모드로 떠 있는지, 환경변수가 무엇인지는 코드로는 알 수 없습니다. **[확인 필요: Vercel 대시보드]**

### 백업
| 종류 | 무엇을 지키나 | 방법 |
|---|---|---|
| GitHub (캠프 공용 저장소 + 개인 저장소 sootdak-ledger) | **코드만**. 숫자는 한 글자도 안 들어 있음 | 커밋·푸시 |
| 백업 파일 (규칙 탭 → JSON 내려받기) | **실제 숫자 전부** (거래·매출·근무·설정·날씨) | 사장님이 손으로 내려받음. `*backup*.json` 은 .gitignore 로 막혀 있음 **[확인]** |
| 복원 | 규칙 탭 → 불러오기 | 현재 데이터를 **통째로 덮어씀** (합치기 아님) **[확인]** |

자동 백업은 없습니다. 마지막으로 백업 파일을 받은 날이 언제인지는 앱이 기억하지 않습니다. **[확인 필요: 사장님]**

## 3. 데이터 손실 위험 요소

새 모듈과 상관없이 지금도 있는 위험부터 적습니다. 위쪽이 더 급합니다.

1. **브라우저 저장소가 유일한 원본.** 브라우저 "인터넷 사용 기록 삭제"에서 사이트 데이터를 지우거나, 다른 브라우저·다른 PC로 열거나, Windows를 다시 깔면 숫자가 사라집니다. 백업 파일이 없으면 복구 불가. **[확인]**
2. **깨진 저장소를 빈 장부로 착각하는 경로.** `readLocal()` 은 저장된 글이 깨져서 못 읽으면 조용히 "빈 장부"를 돌려줍니다. 그 상태에서 숫자 하나를 저장하면 빈 장부 + 새 줄이 원래 자리에 덮어써집니다. 드문 일이지만 일어나면 치명적입니다. **[확인: `lib/storage/local.ts` readLocal·update]** → 새 모듈과 별개로, 못 읽었을 때 경고를 띄우고 저장을 막는 보강을 권합니다.
3. **용량.** localStorage는 브라우저마다 대략 5MB 안팎이 한도이고, 장부 전체가 키 하나에 들어 있습니다. 지금 얼마나 찼는지는 백업 파일 크기로 가늠할 수 있습니다. **[확인 필요: 백업 파일 크기]** 새 모듈이 유동인구·행사 같은 자료를 같은 키에 넣으면 이 한도를 앞당깁니다.
4. **복원은 덮어쓰기.** 오래된 백업 파일을 잘못 불러오면 그 뒤 입력이 날아갑니다. 복원 전에 현재 상태를 먼저 백업하는 습관이 필요합니다.
5. **빌드 사고.** dev 서버가 켜진 채 `next build` 를 돌리면 앱이 안 열립니다(과거 2회). 데이터는 안 날아가지만 사장님이 "다 없어졌다"고 느낄 수 있습니다.
6. **Supabase 시연 DB.** 로그인이 없어 누구나 읽고 쓸 수 있습니다. 가짜 데이터만 둔다는 규칙이 지켜지는 한 손실 위험은 없지만, 실제 숫자를 넣으면 안 됩니다. **[확인]**

새 모듈이 **추가로** 만들 수 있는 위험: 같은 저장 키를 건드리는 것, 날씨처럼 저장소에 자동 저장하는 자료가 커지는 것, 외부 AI에 매출 숫자를 보내는 것(6절). 아래 4절이 그 대비책입니다.

## 4. 안전한 통합 개발 방식

### 원칙
- 기존 파일은 **탭 목록 한 줄**(또는 오늘 탭 카드 한 장) 말고는 손대지 않는다.
- 기존 숫자는 **읽기만** 한다. 쓰는 함수는 새 저장소에만 쓴다.
- 새 자료는 **새 키**에 둔다. 예: `sootdak-market-v1`. 백업 파일에도 따로 묶어 넣는다.

### 폴더 제안
```
lib/market/        계산·외부 데이터 (holidays.ts · events.ts · signal.ts …) + 테스트
lib/storage/market.ts   새 키 전용 읽기·쓰기 (기존 Store 인터페이스는 건드리지 않음)
components/useMarket.ts 화면 상태. 기존 useWeather·useDaily 를 읽기만
app/market/page.tsx     상권분석 화면
```
기존에서 읽는 것: `listAllDailySales()` · `listWeather()` · `getSetting("holidays")` · 채널 목록. 이미 `useWeather.ts` 가 같은 방식으로 읽고 있어 본보기가 있습니다. **[확인]**

### 작업 순서
1. 사장님이 규칙 탭에서 **백업 파일을 하나 받아 둔다.** (작업 전 필수)
2. 캠프 저장소에서 가지(branch)를 하나 판다. 예: `feature/market`. main은 그대로.
3. 고칠 때마다 `npm run typecheck` 와 `npm run test`. **빌드 금지.**
4. 3200 포트 dev 서버가 자동으로 새 화면을 보여 주므로 거기서 확인한다. 실제 숫자가 들어 있는 브라우저이므로 **읽기만 하는지** 특히 본다.
5. 끝나면 main에 합치고 개인 저장소로 복사·커밋. 시연 사이트 배포는 따로 허락받고 `npx vercel deploy --prod`.

### 망가졌을 때 되돌리기
| 상황 | 방법 |
|---|---|
| 코드가 이상함 | `git checkout -- 파일` 또는 가지를 버리고 main으로. 커밋했다면 `git revert` |
| 화면이 안 열림 | dev 서버를 끄고 `.next` 폴더를 지운 뒤 `npm run dev` 다시 |
| 숫자가 이상하게 보임 | 먼저 **현재 상태 백업** → 1번에서 받아 둔 백업 파일로 규칙 탭에서 복원 |
| 시연 사이트가 깨짐 | Vercel 대시보드에서 이전 배포로 되돌리기(Rollback). 로컬 데이터와 무관 |

| 6 | AI 매출 감소 원인 분석 | 💰 + 승인 | 외부 AI API (유료, 열쇠, 서버 코드 필요). 실제 매출 숫자가 외부로 나감 | 요청할 때 | 건당 몇 원~몇십 원 수준 **[확인 필요: 모델·요금]** | 중간~높음 | 하루 단위 몇 달치로는 "원인"을 통계로 못 밝힘. 1단계에서는 AI 없이 규칙으로 "그날 특이점 목록"(비·공휴일·행사·근무 적음)을 보여 주는 게 정직함 |
| 7 | 당일 매출 위험도·기회도 | ✅ 확장 | 이미 있는 `expectedSales` + 최근 4주 같은 요일 평균 + 공휴일·행사 표시 | 매일 자동 | 0원 | 낮음 | 신호등(낮음·보통·높음) 정도. 숫자 맞추기가 아니라 "오늘 준비량 더 할지" 참고용으로만 |
| 8 | 매출 예측·발주량 추천 | ❌ 지금은 | 최소 6개월~1년치 일별 매출 필요. 발주는 원가율 탭의 레시피와 이을 수 있으나 재고·원육 단위 자료가 없음 | - | - | 높음 | 2~4단계 뒤. 지금 만들면 틀린 숫자를 자신 있게 보여 주게 됨 |

### 한 번 더 분명히
- **무료로 "자동" 되는 것**: 날씨(있음), 공휴일, 큰 축제 목록, 당일 신호등, 변수 연계.
- **사장님 손이 필요한 것**: 유동인구(월 1회 숫자 옮겨 적기), 동네 행사.
- **돈 드는 것**: AI 원인 분석, 통신사 유동인구.
- **지금은 안 되는 것**: 예측·발주.

## 7. 단계별 개발 계획

| 단계 | 내용 | 돈 | 사장님이 할 일 |
|---|---|---|---|
| 0 | 백업 파일 받기 · 가지 만들기 · 깨진 저장소 경고 보강(3절 2번) | 0 | 백업 1회 |
| 1 | 상권분석 화면 뼈대(오늘 탭 카드에서 진입) · 공휴일 자동 받기 · 행사 손 입력표 · 당일 신호등 · "그날 특이점" 목록 · 공휴일·연휴 평균 비교 | 0 | 공공데이터포털 가입, 특일정보 열쇠 신청 |
| 2 | TourAPI 청주 축제 자동 수집(API route) · 유동인구 월별 손 입력표(동 5곳) · 저녁 시간대 비 표시 | 0 | TourAPI 열쇠 신청, 월 1회 유동인구 숫자 입력 |
| 3 | AI 원인 분석 (승인 뒤) | 유료 | 어떤 AI를 쓸지, 숫자 외부 전송 허락 |
| 4 | 통신사 유동인구 연결 · 매출 예측 · 발주 추천 | 유료 | 견적 검토. 데이터 1년치 쌓인 뒤 |

1단계는 하루 이틀 분량입니다. 기존 코드는 탭/카드 한 줄 말고는 안 건드립니다.

## 8. 개발 착수 전 승인이 필요한 사항

1. **진입 위치**: 하단 탭 7번째로 넣을지, 날씨처럼 오늘 탭 카드로 들어갈지. (추천: 카드. 폰에서 탭이 꽉 참)
2. **새 저장 키 분리**: 상권 자료는 `sootdak-market-v1` 에 따로 두고 백업 파일에 같이 묶기. (추천: 예)
3. **깨진 저장소 경고 보강**: 기존 `lib/storage/local.ts` 를 한 군데 고치는 일이라 "기존 코드 안 건드림" 원칙의 예외. (추천: 1단계에 포함, 테스트 추가)
4. **공공데이터포털 열쇠 2개 신청**: 사장님 계정으로 특일정보·TourAPI. 무료.
5. **서버 코드(API route) 허용 여부**: TourAPI 열쇠를 숨기려면 필요. 내 PC 모드에서는 `.env.local` 에만 둠.
6. **유동인구는 손 입력으로 시작**해도 되는지. 자동은 무료로 불가.
7. **AI 원인 분석은 3단계로 미루고**, 1단계는 규칙 기반 "특이점 목록"으로 대신해도 되는지.
8. **Open-Meteo 상업 이용 조건 확인** 뒤 계속 쓸지.
