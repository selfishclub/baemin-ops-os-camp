## 1. 사용한 ZIP 라이브러리

**fflate 0.8.3** (사장님 승인 뒤 개발 폴더에만 설치. `package.json`·`package-lock.json` 변경).
- 의존 패키지 없음, 브라우저에 실리는 크기 약 11KB, MIT.
- 사진은 이미 JPEG 라 압축하지 않고 **저장만(level 0)** 한다 → 바이트가 그대로 보존되고 CPU·메모리를 덜 쓴다.
- 해시(SHA-256)는 브라우저 내장 Web Crypto 를 쓴다. 추가 패키지 없음.
- jszip 은 의존 패키지 4개(오래된 `readable-stream` 2.x 포함)와 메모리 사용량 때문에 제외.

## 3. 사진 저장 구조 (코드로 확인)

IndexedDB `sootdak-ledger-photos` / 저장소 `photos` / 키 `id` / 인덱스 `ownerId`.
레코드: `{ id, ownerId, name, type, size, addedAt, blob }`.
- `ownerId` = 영수증(매입) id 또는 고정비 id. 둘 다 장부 설정(`purchases_YYYY-MM`, `fixed_costs`) 안에 있다.
- 사진을 지우는 곳: 영수증·고정비 삭제, 새 영수증 편집 취소. 백업·복원 코드는 지우지 않는다.

## 4. 사진 백업 구조

```
sootdak-ledger-photos-2026-10-09T14-13-52.zip
├─ manifest.json               (압축)
├─ photos/0001_ph_a.jpg        (저장만, 바이트 그대로)
├─ photos/0002_ph_b.jpg
└─ photos/0003_ph_c.png
```
- 경로 규칙: `photos/<순번 4자리>_<id 에서 영숫자·_·- 만 남김, 64자 이내>.<jpg|png|webp|gif|bin>`. 순번이 앞에 있어 **충돌이 없고**, 사용자 파일명은 경로에 쓰지 않는다(manifest 의 `name` 에만).
- 사진 0장: manifest 만 든 ZIP 을 정상으로 만든다 (테스트 1, 브라우저에서도 "장부+사진" 버튼으로 확인).
- 메모리: ZIP 을 통째로 메모리에 만든다. 300MB 넘으면 "다른 탭 닫고 진행" 확인을 받고, **1GB 넘으면 거절**("나눠 받는 기능은 아직 없음"). 만들다 메모리 오류가 나면 그 뜻으로 안내한다.
- 내려받기 뒤 "다운로드 폴더에 파일이 있는지 직접 확인" 안내. 마지막 사진 백업 **시작** 시각을 별도 키에 기록.

## 5. manifest 형식

```json
{
  "app": "sootdak-ledger-photos",
  "format": 1,
  "appVersion": "v2",
  "createdAt": "2026-10-09T05:13:52.979Z",
  "ledgerSavedAt": "2026-10-09T05:14:41.751Z",   // 같이 받은 장부 백업의 savedAt. 따로 받았으면 null
  "ledgerOwnerIds": 12,                          // 백업 당시 장부가 알던 영수증·고정비 id 수 (참고)
  "photos": [
    { "id": "ph_a", "ownerId": "p1", "name": "영수증.jpg", "type": "image/jpeg", "size": 400,
      "addedAt": "2026-09-10T10:00:00.000Z", "path": "photos/0001_ph_a.jpg", "sha256": "…64자…" }
  ]
}
```

**장부와 사진 백업 연결**: 규칙 탭 "장부 + 사진 한 번에 받기"는 장부 JSON 을 먼저 만들고 그 `savedAt` 을 ZIP manifest 의 `ledgerSavedAt` 에 넣는다 → 두 파일이 같은 시점 묶음임을 알 수 있다. 장부 JSON 형식은 그대로(테스트로 확인), 장부 저장소도 손대지 않았다. 따로 받으면 `ledgerSavedAt: null`.

## 6. 복원 및 충돌 처리 정책

미리보기에 표시: ZIP 안 사진 수·총 용량 · 검사 통과 수 · **새로 넣을 사진** · 이미 있어서 건너뜀 · **충돌** · 연결되는 사진 · 연결 안 되는 사진 · 같이 받은 장부 시각.

| 상황 | 처리 |
|---|---|
| ZIP 에만 있는 id | 새 사진으로 추가 |
| 같은 id · 같은 내용(해시 일치) | 건너뜀 (개수 보고) |
| 같은 id · 다른 내용 | **충돌로 표시, 덮어쓰지 않음.** 기존 사진 유지 |
| ownerId | 바꾸지 않음. 장부에 그 영수증이 없으면 "연결 안 됨" 경고(넣어도 화면에 안 보임, 장부 복원 뒤 연결됨) |
| 기존 사진 | 절대 지우지 않음 |
| 확인 | 체크박스 "새 사진 N장을 넣는 데 동의" 를 켜야 버튼 활성. 넣을 사진이 0장이면 버튼 비활성 |
| 실행 | `addPhotosAtomic`: **IndexedDB 한 트랜잭션**, `add` 사용. 하나라도 실패(공간 부족·같은 id)하면 트랜잭션이 통째로 취소 → **전부 들어가거나 하나도 안 들어감** |
| 실패 | "하나도 저장되지 않았고 기존 사진은 그대로" + 원인 + **다시 시도** 버튼(다시 검사·계획부터) |
| 부분 복원 | 트랜잭션 덕분에 생기지 않는다. 혹시 이전 시도에서 일부가 들어갔더라도 다음 시도에서 해시를 다시 재서 "건너뜀" 으로 잡히므로 재시도가 안전하다 (테스트 13) |

원자성의 한계: 한 트랜잭션에 수백 MB 를 넣으면 브라우저가 메모리 때문에 트랜잭션을 취소할 수 있다. 그 경우도 "하나도 안 들어감 + 재시도" 로 떨어진다. 나눠 넣는 기능은 없다.

## 7. 무결성 검사 (`inspectPhotoBackup`)

| 검사 | 실패 시 |
|---|---|
| ZIP 열기 | "손상됐거나 ZIP 아님" 거절 (잘린 ZIP 포함, 테스트) |
| manifest.json 존재·JSON·객체 | 거절 |
| `app` 식별자, `format` 숫자·지원(1) | 거절. 더 큰 형식은 "앱을 새로 받으세요" |
| 항목별: id 있음·중복 없음, ownerId 있음, 경로가 고정 규칙에 맞고 `..` 없음, 경로 중복 없음, size 숫자, sha256 64자 | 거절 |
| 사진 파일이 ZIP 안에 있음 | 없으면 "불완전한 백업" 거절 |
| 크기 일치, **SHA-256 일치** | 거절 |
| manifest 에 없는 파일 | 경고만, 무시 |

검증에 실패한 파일은 복원 단계로 넘어가지 않는다.

## 8. 장부와 사진 연결 검증

- 복원 계획이 지금 장부(`readLocal` → `photoOwnerIds`)의 영수증·고정비 id 로 "연결됨/안 됨"을 가른다 (테스트 14). 장부가 손상 상태면 "연결 확인 불가, 장부 복구 뒤 연결됨" 경고를 띄우고 사진 복원은 허용한다.
- manifest 의 `ledgerSavedAt` 으로 같은 시점 묶음을 판별한다 (테스트 14-2).
- 브라우저: 장부 설정에 영수증 `p1` 만 있는 상태에서 `p1` 사진 2장·`f1` 사진 1장(충돌) → "연결됨 2장, 연결 안 됨 0장" 표시 확인.

## 9. 대용량 처리 한계

- 백업·복원 모두 ZIP 전체를 메모리에 올린다. 사진 한 장 200~400KB 기준 500장 ≈ 150MB 까지는 데스크톱에서 무리 없음 **[추정]**. 300MB 부터 경고, 1GB 부터 거절.
- 검사 단계에서 사진마다 SHA-256 을 계산하므로 수백 장이면 몇 초 걸린다. 진행 표시는 "검사 중" 한 줄뿐.
- 복원 한 트랜잭션 크기 한계는 브라우저마다 다르다 **[확인 필요]**. 실패하면 재시도만 가능, 나눠 넣기 없음.
- 사진을 폰에서 많이 올리는 경우 IndexedDB 자체 용량 한계(브라우저가 디스크 여유에 따라 정함)가 먼저 올 수 있다. 규칙 탭에 사진 수·용량을 표시해 가늠할 수 있게 했다.

## 12. E단계(자동 백업) 전 해결해야 할 문제

1. **서버는 브라우저 저장소를 못 읽는다.** 자동 백업은 앱이 열려 있을 때 브라우저가 장부 JSON 과 사진 ZIP 을 만들어 `POST` 로 서버에 보내는 구조여야 한다. 이번 단계의 `exportBackup()`·`buildPhotoBackup()` 을 그대로 쓰면 된다.
2. **사진 ZIP 크기.** 매번 전체 사진을 보내면 수백 MB 가 날마다 오간다. 사진은 바뀐 것만 보내거나(해시 비교), 하루 1회로 제한하거나, 장부는 매번·사진은 주 1회처럼 주기를 나눠야 한다. 결정 필요.
3. **묶음 일관성.** 장부 JSON 과 사진 ZIP 을 따로 보내면 하나만 성공할 수 있다. 서버가 둘 다 임시 파일로 받은 뒤 검증이 끝났을 때만 최종 이름으로 바꾸고, 하나라도 실패하면 "불완전" 으로 기록해야 한다.
4. **보안.** localhost 출처 검사만으로는 부족하다. 앱이 처음 켜질 때 서버가 만든 1회용 토큰을 환경변수(`.env.local`)와 맞춰 보는 식의 추가 검증, 요청 크기 상한(예: 1.2GB), 경로 고정, 로그에 내용 미출력, Vercel(시연)에서는 라우트 비활성이 필요하다.
5. **서버 측 해시 검증.** ZIP 안 manifest 의 SHA-256 을 서버에서 다시 계산해 맞춰야 "기록 완료" 로 칠 수 있다. Node 의 `crypto` 로 가능, 패키지 불필요. ZIP 을 서버에서 풀려면 fflate 를 서버 코드에서도 쓰면 된다.
6. **백업 폴더.** 운영 폴더 `C:\Users\ksg39\Documents\손익장부백업` 은 승인 전 생성 금지. 테스트는 `…\손익장부백업-테스트`.
7. **마지막 백업 시각의 뜻.** 자동 백업이 생기면 "서버가 검증까지 끝낸 시각" 을 따로 기록해, 지금의 "내려받기 시작 시각" 과 구분해야 한다.
8. **후속 과제 유지**: 여러 번 저장하는 흐름의 부분 저장(B단계부터), 사진 나눠 받기.
