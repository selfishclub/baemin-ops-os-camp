## 2. 자동 백업 구조

```
브라우저(3201 화면)                          로컬 Next 서버(127.0.0.1:3201)              PC 폴더
  장부 JSON = exportBackup()                                                          
  사진 ZIP  = buildPhotoBackup()                                                      
  POST /session ──────────────────────▶ 세션 토큰 발급(메모리)                          
  POST /upload (ledger, id, sha) ─────▶ ledger-<id>.part 로 스트림 저장, 해시 비교 ──▶ .part
  POST /upload (photos, id, sha) ─────▶ photos-<id>.part                            ─▶ .part
  POST /finalize {id, 해시, 크기, 수} ─▶ .part 를 다시 읽어 해시·크기·구조 검증
                                        → ledger-날짜-시각-id.json (EXCL 복사)      ─▶ 최종
                                        → photos-날짜-시각-id.zip                     ─▶ 최종
                                        → 복사본 다시 읽어 해시 확인
                                        → backup-manifest-날짜-시각-id.json           ─▶ 최종
                                        → .part 삭제
  ◀── manifest {verified:true} ────────  (여기서만 "성공"으로 기록)
```
- 서버는 브라우저 저장소를 읽지 못하므로 **브라우저가 열려 있을 때만** 돈다. 카드 하단과 꺼짐 안내에 명시.
- 전송은 `fetch` 본문을 그대로 보내고, 서버는 `req.body` 스트림을 디스크로 흘려 쓴다. **메모리에 파일 전체를 올리지 않는다** (App Router 라우트 핸들러는 본문 크기 제한을 두지 않으므로 우리 쪽 상한으로 끊는다).

## 3. 백업 주기 (구현된 정책)

| 상황 | 동작 |
|---|---|
| 장부 저장 성공 | 변경 시각 기록 → **30초 debounce** → 전송. 연속 저장은 마지막 것 기준 1회 |
| 사진 추가·삭제 | 변경 시각 기록 → 같은 debounce → 사진이 바뀌었으면 **전체(장부+사진)** 로 |
| 앱 실행 | 세션·상태 확인 → 8초 뒤 밀린 백업. 마지막 전체 백업이 24시간 넘었거나 없으면 전체 |
| 전체 백업 | **하루 1회** (24시간 간격). 30분마다 다시 확인 |
| 실패 | 2분 → 4분 → 8분 → 16분 → 30분 간격 재시도. **3번 연속 실패하면 빨간 경고**, 6번이면 자동 재시도 중단(수동 버튼으로 재개) |
| 완료 판정 | `isFullyBackedUp` = 전체 백업 성공 + 그 뒤 장부·사진 변경 없음. **사진이 바뀐 뒤 장부만 성공하면 "전체 완료"로 표시하지 않음** (테스트·화면 문구) |
| 삭제 | 서버도 브라우저도 백업 파일을 지우지 않음. 폴더 정리는 사장님이 |

## 5. 백업 파일 구조와 검증

파일 이름: `ledger-YYYYMMDD-HHMMSS-<uuid>.json` · `photos-…-<uuid>.zip` · `backup-manifest-…-<uuid>.json`. 시각은 **서버 시각**, uuid 는 브라우저가 만들고 서버가 형식(`8-4-4-4-12` 16진수)을 검사. 장부와 사진은 **같은 uuid**.

manifest (실제 테스트 산출물):
```json
{ "app": "sootdak-ledger-backup", "format": 1, "id": "88dcbf82-…", "mode": "full",
  "createdAt": "…(브라우저)", "storedAt": "…(서버)",
  "ledger": { "file": "ledger-20261009-145737-88dcbf82-….json", "sha256": "5c6ad7…", "size": 719, "transactions": 1, "dailySales": 0 },
  "photos": { "file": "photos-20261009-145737-88dcbf82-….zip", "sha256": "c0a268…", "size": 1504, "count": 2 },
  "verified": true, "verifiedAt": "…" }
```
`mode: "ledger"` 면 `photos: null`. 불완전 백업은 `backup-manifest-…-<uuid>.incomplete.json` 에 `verified:false, error` 로 남는다.

서버 검증 순서(마무리): 임시 파일 존재 → 크기 일치 → **디스크에서 다시 읽은 SHA-256 = 브라우저가 말한 값** → 장부는 `inspectBackup`(C단계 검사기) 통과 → 사진은 `inspectPhotoBackup`(D단계 검사기) 통과 + 장수 일치 → EXCL 복사 → **복사본을 또 읽어 해시 재확인** → manifest. "파일이 있다"로 성공을 판정하는 곳은 없다.

안전한 기록: 임시 파일 `.part` 는 `wx`(있으면 실패) 로 열고, 최종 파일은 `COPYFILE_EXCL` 로 만든다(덮어쓰기 금지). 실패한 `.part` 는 서버가 지운다(자기가 만든 것만). 브라우저가 중간에 닫혀 남은 `.part` 는 지우지 않고 상태에 "임시 N개"로 보여 준다(사장님이 정리).

## 7. 백업 실패·재시도 처리

- 실패 종류별 메시지: 디스크 부족(ENOSPC) · 권한(EACCES) · 같은 이름 있음(EEXIST) · 해시 불일치 · 구조 불량 · 크기 초과 · 세션 만료(401 → 토큰 버리고 새로 받음).
- 재시도는 3절 간격. 재시도 때마다 **새 uuid** 로 처음부터(업로드→마무리) 다시 하므로 반쯤 남은 상태를 이어받지 않는다.
- 동시 실행 방지: `running` 가드로 두 번째 요청은 무시. 서버도 같은 uuid·종류 임시 파일이 있으면 409.
- 브라우저 닫힘: 성공 기록이 없으니 다음에 열면 같은 백업을 다시 계획한다(테스트 6). 서버에 남은 `.part` 는 성공으로 세지 않는다.

## 8. 장부·사진 일관성 검증

- 전체 백업은 장부·사진이 **같은 uuid** 를 갖고 manifest 한 개에 둘 다 적힌다. 하나라도 검증 실패면 둘 다 최종 파일이 되지 않는다(불완전 기록만).
- 장부만 백업(`mode: ledger`)과 전체(`mode: full`)를 manifest 와 상태 카드가 구분한다.
- 화면의 "전체 완료"는 사진 변경 시각 ≤ 사진 백업 성공 시각일 때만 (테스트 4-4).
- 저장된 파일을 C·D단계 검사기로 다시 읽어 복원 가능함을 테스트(17)와 수동(해시 재계산 일치)으로 확인.

## 9. 대용량 처리 한계

- 서버 수신은 스트림이라 메모리 부담이 작지만, **마무리 때 검증을 위해 파일 전체를 한 번 읽는다** (장부는 작음, 사진 ZIP 은 수백 MB 가능). 1.2GB 상한.
- 브라우저는 D단계와 같이 ZIP 을 메모리에 만든다(300MB 경고·1GB 거절 규칙은 수동 백업 카드에만 있고, 자동 백업은 ZIP 생성 실패 시 오류로 기록·재시도).
- 사진이 많으면 하루 1회 전체 백업이 수백 MB 씩 폴더에 쌓인다. 바뀐 사진만 보내는 증분 백업은 없다(F단계 뒤 과제).

- 없음. 운영 폴더·3200·실제 저장소 미접근. 가지에 로컬 커밋만.
- 운영 반영 시: `BACKUP_DIR` 을 적기 전까지 자동 백업은 "꺼짐"으로만 보이고 아무 일도 하지 않는다. 켜면 규칙 탭 카드와 백업 폴더가 생긴다. 다른 화면·장부 동작은 동일.
- 참고: 앞 보고서에서 언급한 운영 폴더의 추적 안 된 파일 2개는 지금은 보이지 않는다(정리된 것으로 보임).

## 12. F단계(전체 회귀 테스트) 전 해결해야 할 문제

1. **운영 3200 의 바인딩.** 현재 `0.0.0.0`. G단계 반영 때 실행 명령을 `next dev -H 127.0.0.1 -p 3200` 으로 바꿀지 결정(README·시작 스크립트 수정).
2. **운영 백업 폴더 생성 승인** 과 운영 `.env.local` 에 `BACKUP_DIR` 추가(기존 Vercel 토큰 줄은 그대로).
3. **증분 사진 백업 없음.** 사진 수백 장이면 하루 수백 MB. F단계 회귀 테스트 때 "사진 200장(60MB) 가짜"로 시간·메모리를 재 볼 것.
4. **폴더 용량 안내.** 카드에 총 용량은 보이지만 "디스크 여유" 는 모른다. 디스크 부족은 실패로만 알게 된다.
5. **`.part` 잔여 파일 정리** 는 사람이. 자동 삭제 금지 원칙 때문.
6. **후속 과제 유지**: 여러 번 저장 흐름의 부분 저장(B), 사진 나눠 받기(D).
